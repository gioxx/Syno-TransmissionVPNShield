Frequently asked questions

Common questions about activation, routing, and the forwarded port. See the full documentation for details.

Why does the package need a Task Scheduler step to activate?

DSM 7.2+ blocks unsigned third-party packages from declaring root privileges at install time. The package installs as a normal user, and a one-time root Task Scheduler job completes the elevation and applies the routing rules.

Does the shield manage my VPN connection?

No. It assumes VPN_IF (default tun0) is already up, managed by DSM's VPN Center or a third-party OpenVPN/WireGuard client. The shield only routes Transmission's traffic through whatever interface is already there.

What happens if the VPN drops?

The dedicated routing table gets a blackhole default route (IPv4 and IPv6) instead of being left empty, so Transmission's traffic is dropped rather than falling through to the main table and leaking - even on kernels without the xt_owner kill switch.

Do I need to open the forwarded port on my router or DSM firewall?

No. The forwarded port arrives through the VPN tunnel itself; nothing needs to be opened locally.

Why does Transmission stay stopped after I upgrade the shield?

The shield always stops Transmission when it goes down, but by default never starts it again, so an upgrade or reboot leaves it stopped until you start it yourself. Set AUTOSTART_TRANSMISSION="1" in guard.conf to have the shield restart Transmission automatically, only once the VPN is up and routing is applied.

My NAS doesn't support the kill switch - am I still protected?

Yes. Many DSM builds ship without xt_owner support, but protection does not depend on it: the fail-closed blackhole route already drops Transmission's traffic whenever the VPN is down, kill switch or not.

What if my NAS doesn't support per-UID IPv6 rules?

Older DSM 7.0/7.1 low-end models (kernel 4.4) can't policy-route IPv6 by UID. The shield still protects IPv4 fully and logs a one-time warning; set IPV6_MODE="off" in guard.conf to silence it.

The forwarded port isn't updating in Transmission - why?

If Transmission has RPC authentication enabled, the shield needs matching credentials in the root-only etc/guard.secret file (RPC_USER / RPC_PASS), separate from the world-readable guard.conf. Without them the push fails with an HTTP 401.

How do I recover from an Uptime Kuma heartbeat down?

Since 0.2.0 the reconcile daemon fixes most causes on its own within RECONCILE_INTERVAL_SEC. If it stays down, run /var/packages/transmission-vpn-shield/scripts/recover-heartbeat (as a Task Scheduler script) - it stops Transmission, restarts the shield, then starts Transmission again.

Where are logs stored?

All shield activity is written to var/shield.log (size-capped, no rotation config needed) and shown in the web UI's log panel.

Do I need to re-run activate after every upgrade?

Yes. DSM resets the privilege file on every package upgrade, so activate needs to run again as root to restore it.

Transmission VPN Shield
