Overview

Transmission VPN Shield is a Synology SPK that forces Transmission's traffic through a VPN interface with UID-based policy routing - IPv4 always, and IPv6 too on DSM kernels ≥ 4.10 (older low-end boxes get IPv4-only protection plus a one-time warning) - while the web UI, Sonarr/Radarr, and the rest of the LAN keep working normally.

A background reconcile daemon re-applies the routing on a timer, so the shield heals itself after a VPN reconnect, a reboot, or an unlucky boot order. When the tunnel is down it fails closed: a blackhole route drops Transmission's traffic instead of letting it leak, even on DSM kernels without the xt_owner kill switch.

Installation

Why the extra step? DSM 7.2+ blocks unsigned third-party packages from declaring root privileges at install time. The package installs as a normal user, then a one-time Task Scheduler job completes the elevation and applies the routing rules.

Step 1 - Install the package

  • Download the latest .spk from the Releases page.
  • In DSM → Package Center → top-right menu → Manual Install, upload the .spk.
  • The package will show as Installed (not running). Open its web UI - it will display an activation guide.

Step 2 - One-time activation via Task Scheduler

This step applies the routing rules as root. Run it once after install and again after any upgrade.

  1. In DSM → Control Panel → Task Scheduler → Create → Triggered Task → User-defined script.
  2. Task name: anything you like. User: root. Leave Enabled unchecked.
  3. In Task Settings, paste one of these commands:

Without VPN forwarded port:

/var/packages/transmission-vpn-shield/scripts/activate

With VPN forwarded port (replace 56460 with yours):

/var/packages/transmission-vpn-shield/scripts/activate 56460

Click OK, select the task, click Run. After a few seconds the web UI should show the shield as active - use its Check activation status button to confirm.

Step 3 - Start Transmission

Once the shield is active, start Transmission from DSM → Package Center → Transmission → Start so it launches through the VPN tunnel. The shield always stops Transmission when it goes down, but by default never starts it, so you also do this after every shield upgrade. Set AUTOSTART_TRANSMISSION="1" in guard.conf to have the shield restart Transmission for you (only once the VPN is up and routing is applied).

Step 4 - Web UI

The shield icon appears in the DSM Main Menu, and the web UI is also directly reachable at:

http://<your-nas-ip>:5000/webman/3rdparty/transmission-vpn-shield/index.cgi

Configuration

The config file lives on the NAS at:

/var/packages/transmission-vpn-shield/etc/guard.conf

This is the folder DSM actually preserves across upgrades. Edit it directly, or use activate / set-port, which write to it correctly. After editing, restart the package from DSM Package Center. With the default AUTOSTART_TRANSMISSION="0", restarting the shield stops Transmission and leaves it stopped - start it again from Package Center → Transmission → Start once the shield is green, or set AUTOSTART_TRANSMISSION="1" to have it restart automatically.

New keys introduced by an upgrade are appended to your existing etc/guard.conf automatically, so you never lose settings and never have to hand-merge the template.

Forwarded port

Some VPN providers let you forward a port through the tunnel, allowing other peers to connect directly to you - this significantly improves speeds and seeding ratios. You do not need to open this port on your router or DSM firewall; traffic enters through the VPN tunnel.

Option A - at activation time (easiest, no SSH):

/var/packages/transmission-vpn-shield/scripts/activate 56460

Option B - after activation, via Task Scheduler as root:

/var/packages/transmission-vpn-shield/scripts/set-port 56460

Option C - edit guard.conf directly, then restart the package from Package Center:

FORWARDED_PORT="56460"

RPC authentication

The shield sets Transmission's peer port over RPC (127.0.0.1:${RPC_PORT}). If Transmission has "Enable authentication" checked in its Remote Access settings, unauthenticated RPC calls get an HTTP 401 and the port push silently fails. Put the credentials in the root-only secret file:

/var/packages/transmission-vpn-shield/etc/guard.secret
RPC_USER="youruser"
RPC_PASS="yourpass"

guard.secret is created empty on install and chmod 600, so the world-readable guard.conf never carries the password. Restart the package after editing.

Uptime Kuma monitoring

If you run Uptime Kuma somewhere on your network, the shield can push its health to a "Push" monitor every minute. The NAS only makes outbound HTTPS requests - nothing new is exposed on the LAN, and the per-monitor URL Kuma generates acts as the token.

On every tick the daemon evaluates the same checks shown in the web UI: VPN interface state, routing table/rule/route, IPv6 protection, reconcile-daemon liveness, kill-switch presence, and a cached Transmission port-test. Status is up only when VPN, IPv4 routing, and IPv6 protection (unless IPV6_MODE=off) are all in place and the port-test result is not closed.

Setup:

  1. In Uptime Kuma, create a Push monitor and copy its unique URL.
  2. On the NAS, set KUMA_PUSH_URL="https://kuma.example.com/api/push/abc123" in guard.conf.
  3. Restart the package from DSM Package Center, or sudo synopkg restart transmission-vpn-shield via SSH.

Test a single push without restarting the package:

sudo /var/packages/transmission-vpn-shield/scripts/guard-push once

Since 0.2.0 the reconcile daemon fixes most "down" causes on its own within RECONCILE_INTERVAL_SEC. If a heartbeat stays down, /var/packages/transmission-vpn-shield/scripts/recover-heartbeat automates the full reset (stop Transmission, stop the shield, start the shield, start Transmission) as a Task Scheduler script.

How it works

activate (run as root via Task Scheduler): optionally writes FORWARDED_PORT, runs postinst to elevate privileges and seed config, then calls start-stop-status start directly as root before notifying DSM.

reconcile (the heart, run once by start then on a timer): idempotent and silent unless something actually changes. It loads config, resolves the Transmission UID, keeps the dedicated routing table populated (VPN route when up, blackhole when down, for both IPv4 and IPv6 per IPV6_MODE), re-asserts the UID rules and kill switch, and pushes FORWARDED_PORT to Transmission only when the current peer port differs.

start resolves the UID, runs one reconcile, and starts the background daemons (public-IP refresher, reconcile, Kuma push if configured). With AUTOSTART_TRANSMISSION=1 it restarts Transmission, but only once the VPN is up and the route is in place.

stop / prestop stops the reconcile daemon first, then removes rules, flushes routes, stops the other daemons and Transmission, and sends a final Kuma down.

Web UI (index.cgi) runs as the DSM web server user, not root, and never reads guard.secret.

Limitations

  • VPN not managed: the package does not manage the VPN connection itself; it assumes VPN_IF is already up.
  • Recovery latency, not instant: the reconcile daemon is a timer (default 30s), not event-driven.
  • IPv6 per-UID rules need kernel ≥ 4.10: older low-end DSM boxes protect IPv4 fully and log a one-time warning; set IPV6_MODE="off" to silence it.
  • Kill switch requires xt_owner: many DSM builds ship without it, but protection does not depend on it - the blackhole route already fails Transmission closed.
  • Rules not removed on a non-root Package Center stop: if the privilege file hasn't been updated by activate, ip rules/routes may persist until reboot.
  • Re-run activate after upgrade: DSM overwrites the privilege file on every package upgrade.
